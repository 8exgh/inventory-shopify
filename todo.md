  - I custom built this shopify inventory reload app MVP for a friend's discgolf store. The shopify integration I used is no longer supported by current shopify. I need you to understand how the legacy shopify integration is applied to this custom app. This custom app I built from scratch using my personal way of doing CQRS + ES (Command Query Responsibility Segregation + Event Sourcing). For MVP my philosophy is to avoid optimizing up front. When a read model is built, it's projected from all of the sqlite db row events since the beginning of time. I don't cache for MVP. The UI / and Commmand/Query APIs are in one app. A command validates inputs but also projects all events in sqlite db since beginning of time to figure out current state; if it is valid to do the command based on current state one or more events are emitted (appended) to the sqlite database. Queries most often are a projection of all events since beginning of time (read every single call) into whatever the read model shape needed is. However, it is permissible for a query api endpoint to read directly from shopify integration for the ui. The second type of app in my CQRS + ES stack is the background processor. The background processor has different types of jobs as I need to build out workflows. The background processor will ask a query endpoint if there is any work for the job. If there is, that job in the background processor will try to process the first item. If it succeeds (work can be completed such as updating shopify) then the job will attempt to call a CQRS+ES command endpoint to record that the work in shopify etc completed. If it failed it often will call a command endpoint to record that it failed; that way it can be removed from the work to do list for that type of job or it can contribute to how many retries are remaining before it's not in the list of the query endpoint for the work. That's the general way I approach things. The CQRS+ES sqlite db (events table) is the set of all workflow steps (append only to event table).
